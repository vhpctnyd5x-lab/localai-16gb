# LocalAI 16GB Mac

この公開 repo は、16GB・GPU なしの Mac で Qwen3-30B-A3B Q2_K を llama.cpp で動かし、早く・安く・賢く使う実験と道具をまとめています。
「頭脳」はローカル LLM、「カーネル」は決まった仕事を確実に実行する手下の仕組みです。
モデルを大きくせず、考える手数やプログラムの道具で仕事を改善できるかを測っています。

過去の実験と訂正は [LOG.md](LOG.md)、独自用語と一般用語の対応は [YOUGO.md](YOUGO.md) を見てください。

### 言えないこと

この算数・論理問題集だけから、量子化方式全般の優劣、一般的な推論能力、GPU 機での性能差は結論できません。120問の飽和結果で量子化間に差を検出できなかったことは、差が無い証拠ではありません。訂正済みの古い主張は [LOG.md](LOG.md) に記録しています。

## いま調べていること（2026-09-25 時点。結論ではありません）

- **8GB の機械で同じモデルを動かす**: 今の Q2_K（10.5GB）は 8GB 上限だと 書きが約3割の速さ（4.4 t/s）。専門家を 96個に刈って IQ2_XXS にすると 5.92GiB（PPL +12.8%）。正解率と 8GB 上限の速さを測定中（[dougu/jikken/KEKKA.md](dougu/jikken/KEKKA.md)）。
- **同じ大きさで少し賢く**: Q8_0 から imatrix で作り直した Q2_K は PPL 7.81 → 7.64 と良くなったが、正解率（テストE）は x64 −7問・arm +1問で 上がらなかった（不採用）。PPL だけでは決めない。
- **速さ**: 出力の辞書を 99.99% に絞ると 同じ機械の基準比 1.07〜1.08 倍で 正解率は同じ。専門家を問いごとに減らす方法は 実際の問題では 1.00 倍で効かなかった。
- **ブレの幅**: 温度0.7・種を変えた 5回で x64 85.0%（82.4〜87.2）、arm 82.6%（80.8〜84.0）。温度0の本番（84.8% / 82.4%）は幅の真ん中で、±3点（4問）以内の差は ブレと区別できない（[dougu/bure_matome.py](dougu/bure_matome.py)）。
- **頭脳とカーネルの協働**（[kernel/](kernel/)）: 頭脳が1手ずつ道具を選び、カーネルが門番を通して実行・確認する。アプリで実際に起きた失敗（中身を聞くと数だけ答える・聞き返しが通じない 等）を直し、手元の頼み約30問（テストG）で測る。

## はじめかた（そのまま動きます）

**特別なモデルは要りません。** 上の表は、誰でも落とせる素のモデルで測っています。

### 1. llama.cpp を用意する

```bash
# ★ 版を固定する。固定しないと、テンプレート処理も量子化カーネルも速度も
#   日によって別物になり、この README の数字を再現できない。
git clone https://github.com/ggml-org/llama.cpp
cd llama.cpp && git checkout fa67698 && cd ..   # 2026-09-10 の測定に使った版
cd llama.cpp && cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
```

### 2. モデルを落とす（10.5 GB）

```bash
curl -L -o Qwen3-30B-A3B-Q2_K.gguf \
  https://huggingface.co/unsloth/Qwen3-30B-A3B-GGUF/resolve/main/Qwen3-30B-A3B-Q2_K.gguf
```

### 3. サーバーを立てる

```bash
./llama.cpp/build/bin/llama-server -m Qwen3-30B-A3B-Q2_K.gguf \
  -ngl 0 -c 8192 -np 1 -cb --spec-type ngram-simple -ctk q8_0 -ctv q8_0 \
  --host 127.0.0.1 --port 8080
```

`-ngl 0` は CPU だけで動かす指定です。GPU があるなら `-ngl 99` にしてください。

### 4. 深さを変えて聞いてみる

```bash
python3 kangaeru_fukasa.py "12個のりんごを3人で分けて、余りは箱に戻します。余りは何個？"
```

4つの深さを順に試して、秒数と一緒に出します。

```python
import kangaeru_fukasa as KF
r = KF.kiku("…", fukasa=2)     # 0〜3
print(r["text"], r["考えた字数"], r["回数"])
```

Python 側の依存は **ありません**（標準ライブラリだけ）。
ただし llama.cpp を建てるのに **CMake と C++17 のコンパイラ**が要ります。

### 5. 自分の環境で測り直す

```bash
python3 monosashi/tsukuru.py --kazu 120     # 問題集を作る
python3 monosashi/hakaru.py --fukasa 0      # 深さ0 で解かせる
python3 monosashi/hakaru.py --fukasa 2      # 深さ2 で解かせる
```

段ごとの正解率と、1問あたりの秒数が出ます。

## 測り方

- 自作の問題集で測ります。問題の作り方、不具合の切り分け、訂正履歴は [LOG.md](LOG.md) にあります。
- GitHub Actions で無料測定し、結果は kekka 枝に記録します。普段は自作テストを使い、公式 GSM8K は大きな変更のときの基準にします。
- 速さや正解率は、同じ機械・同じ条件の基準モデルとの比で読みます。1回の測定は1回の数字として扱います。
- 見た問題集の改善だけでは採否を決めず、別に用意した未見の問題集でも確認します。複数の物差しが一致しない場合は、強い結論にしません。
- 道具が使える問題は数え上げなどの決まった計算をプログラムに任せます。型が合う問題だけに適用し、モデルの出力と計算結果の確認が一致しない場合は回答を出さない方針です。
- データと測定手順: monosashi/、dougu/、[dougu/jikken/KEKKA.md](dougu/jikken/KEKKA.md)。

### 数字の読み方

- 問題数、モデル、実行環境、深さ、道具の有無を揃えた比較だけを直接比べます。
- 公式ベンチマークと自作テストは別の目的で使います。公式 GSM8K は大きな変更の基準、自作テストは段階的な改善を調べるための問題集です。
- 自作問題は教材や既知問題との重なりを確認し、別の先生による検品と、強いモデルでの解答確認を通します。欠陥が見つかった型は集計から外します。
- 外部から紹介された新技術も、説明や流行だけで採用せず、この Mac と同じ物差しで測った記録を残します。
- 誤りの指摘は、コード・問題文・測定ログを実際に確認して、当たっているものと当たっていないものを分けて記録します。
- 効果が複数の独立した確認で一致しない場合や、測定の条件が足りない場合は結論を保留します。
- 結果は基準との差と一緒に残し、見た問題だけで改善した場合は未見問題で再確認します。

## ことわり

- 測定は Intel Mac / CPU推論 / 16GB という特殊な条件です。Apple Silicon や GPU では、とくに速度まわりの結論が変わります。
- 120問は算数・数え上げ・日付・論理に寄っています。文章を書く力や会話の自然さは測っていません。
- 数値は記載した機械・モデル・問題集・実行条件での観測です。再現にはモデルと llama.cpp の版、実行条件を合わせてください。測定の誤差や未確認事項は各記録に記しています。
- モデルの重みは含みません。ライセンスは元モデル（Qwen3）に従ってください。
